# B站多节点加速器（油猴脚本）v0.2.1

接管 B 站播放器的视频分段请求：先把整段交给最合适的 CDN 节点（默认就是 B 站自己选的那个），一边下载一边预测能不能赶上播放；预计赶不上时，把还没下的部分按各节点速度切开，交给多个节点并行拉取，拼好后按顺序交还给播放器。播放器本身不需要任何改动。

## 安装

1. 在 Chrome / Edge 里装好 **Tampermonkey**（篡改猴）扩展。
2. 打开 Tampermonkey 管理面板 → 「+」新建脚本（已装旧版的话点开旧脚本）→ 把 `bilibili-accelerator.user.js` 的全部内容粘进去，替换原有内容 → 保存。
3. 打开任意 B 站视频页，左下角会出现一个 **⚡** 小按钮。

只在 `www.bilibili.com/video/`、`/bangumi/play/`、`/list/` 等播放页生效，其他页面不加载。

## 使用

- 点 **⚡** 或按 **Alt+Shift+B** 打开面板：
  - **已接管请求**：大于 0 说明脚本在起作用；一直是 0 说明 B 站播放器的下载方式没被接管（见"已知限制"），此时脚本不影响播放。
  - **落后拆分 / 救援 / 探索 / 播放卡顿 / 内容不一致 / 回退原请求**：调度器各类动作的次数。
  - 节点表：每个 CDN 节点的状态（冷启动 / 已测 / 探索中 / 暂停 / 失效 / 内容不一致）、评分、速度、首包时间、按时与迟到次数等。
- **启用**：取消勾选就不再接管新请求，等同于没装。
- **落后时拆成**：不拆 / 2 路 / 3 路（默认）/ 4 路。
- **试探 upos 镜像**：用同一个签名额外试几个官方 upos 镜像，不通的会自动标为"失效"。
- **控制台日志**：在开发者工具控制台输出调度细节。

## 反馈问题：复制诊断信息

面板上的 **复制诊断信息** 会把以下内容复制到剪贴板，直接粘贴发出即可：

- 每个视频分段请求是经 fetch 还是 XHR 发出的、有没有被接管；没接管的话写明原因（没带 Range、文件不在节点池里、请求太小、responseType 不对、开关被关掉等）。
- 页面有没有拿到节点池（`__playinfo__` / playurl 接口），登记了哪几路流、各有哪些节点。
- 页面创建的 Worker，以及浏览器资源计时里记录的视频请求，用来判断播放器是不是在 Worker 里下载。
- 调度统计、节点表和最近 150 行日志。

为了保护隐私，所有链接只保留**域名和文件名**，去掉了签名、用户 ID 等参数。诊断里还会带上浏览器 UA 和当前页面路径（含 BV 号）。

在开发者工具控制台里执行 `copy(__biliAccelDiag())` 也能得到同样的内容。

## 原理

| 机制 | 做法 |
|---|---|
| 整段优先、落后时动态拆分 | 播放器的一段请求先整段交给一个节点。下载中每 150ms 按实际速度预测完成时间；预计赶不上截止时间时，把还没下的部分按各节点的速度和首包时间算出最优分配，现场切开交给原节点和其他 1~3 个节点并行拉取，原请求被截短。节点正常时只有一个请求，没有额外开销。 |
| 播放截止时间 | 截止时间 = 缓冲按当前倍速耗尽的时刻，但**最多 1.5 秒**：真实页面诊断显示，B 站播放器约 2 秒拿不到数据就会取消并重发同一段，缓冲再多也没用。整段共用一个截止时间；拖动后缓冲为空时，给 0.5 秒的起播目标。 |
| B 站首选节点优先 | 紧急请求默认交给播放器本来要请求的节点（B 站的首选）。只有别的节点在**可靠的大传输**（≥1MB，至少 2 次）里被测出明显更快（耗时不到首选的 35%）才换。首选节点还没做过大传输时会给它一次机会，但被救援过、失败过或抢跑时没到场的不再给。 |
| 冷启动抢跑 | 起播时让首选节点和另一个候选节点同时拉同一段，两边都测出速度后，按**预计谁先下完**判胜负（首选节点打 7 折，抵消短时测速偏差）。输家已收到的数据核对一致后直接用上；没测到速度的节点之后还会再给机会（每路流最多 3 轮）。 |
| 预测性救援 | 请求真正卡住（迟迟等不到首包，或超过 1 秒没有新数据）时，**立即**让别的节点拉剩下的字节，不管离截止时间还有多远；先拼完整的一方胜出，其余请求立即取消。 |
| 后台探索（陪跑） | 缓冲超过 8 秒、最近 10 秒没卡顿时，让一个没测过的节点和已知节点**同时**拉同一段，按抢跑规则判定。已知节点照常在拉，所以探测节点再慢、再不通也不会让这一段卡住。从没成功过的节点连续失败或没到场 2 次就停用（多为签名不通用的镜像）。 |
| 动态信誉 | 每个节点有 0~1 的评分，跟当前这一路流绑定：按时交付慢慢回升；被救援 ×0.75；造成播放卡顿 ×0.6；出错暂停 30 秒、评分减半；403/404 直接判失效。各节点的历史速度跨页面保存，只用于冷启动时排序。 |
| 跨节点内容一致性 | ① 同一路流各节点返回的文件总长度必须相同，不同的节点立即停用；② 抢跑时核对输家已收到的字节和赢家是否一致；③ 从中间开始拉的请求多拉前面 4KB 已有的数据，交付前逐字节核对，对不上就整段作废、停用该节点，交回播放器重试。 |
| 失败处理 | 分段失败会换节点重试；所有节点都失效，或者在交付任何数据前出错，原请求原样交回给播放器（"回退原请求"计数 +1），播放器感知不到。 |

## 真实 B 站页面实测（2026-10-25，v0.2.0，登录 4K）

来自用户贴回的诊断信息：
- **能接管**：播放器在主线程用 XHR 下载分段（Worker 里没有下载），88 个分段请求被接管，共 339MB。
- 全程**播放卡顿 0 次**、内容不一致 0 次、回退原请求 0 次；落后拆分 45 次、救援 15 次。
- 发现的问题（已在 v0.2.1 修复）：
  - 播放器约 2 秒超时重发。
  - 反复卡住的首选节点仍被优先选用，每次要卡约 1.5 秒才被救走。
  - 探索时把整段交给了不通的镜像。
  - 统计上报被误记为视频请求。

## 实测（真实 B 站 CDN，联通 1000M，未登录 480P）

每个视频选 10~12 个拖动位置，每次请求 3~4MB，"单节点（播放器原本的做法）"和"加速器"轮流跑。单位 ms，格式为整段下完的**中位数 / P90**（最慢的 10%）。

**2026-10-25 凌晨，v0.2.0（当前版本，首选节点恋旧）：**

| 视频（B 站首选节点） | 单节点 | v0.2.0 |
|---|---|---|
| Rick Astley（mcdn） | 66 / 112 | 66 / 128 |
| 98 分钟视频（mcdn） | 160 / 230 | 183 / 284 |
| 14 小时合集（PCDN） | 280 / 653 | 256 / 767 |

**2026-10-24 晚高峰，v0.1（固定 1MB 分块）：**

| 视频（B 站首选节点） | 单节点 | v0.1 |
|---|---|---|
| Rick Astley（mcdn） | 68 / 158 | 109 / 162 |
| 14 小时合集（PCDN） | 102 / 604 | 256 / 371 |
| 98 分钟视频（PCDN） | 258 / 589 | 120 / 242 |

**怎么看这些数据：**
- **B 站首选节点状态好时，原播放器已经很快，加速器只能做到持平或略慢**（多一次抢跑、偶尔被短时测速误导）。
- **首选节点变慢时，加速器能砍掉慢的那一截**（10-24 晚高峰 P90 降了约一半）。
- CDN 速度波动非常大，同一个视频前后两轮能差好几倍，以上只是这两个时段的样本。

## 已知限制

- 真实 B 站页面上已确认能接管（v0.2.0，见上文）；v0.2.1 的修复还没在真实页面上跑过，只在 Node 模拟测试（25 项）和浏览器本地模拟 CDN 中验证过。如果 B 站以后改成在 Web Worker 里下载分段，脚本会接管不到：面板"已接管请求"一直是 0，但不影响播放。
- **中途截短或取消请求会断开连接。** B 站的 PCDN 节点多为 HTTP/1.1，断开后下一次请求要重新握手，TCP 也要从头提速，所以这类节点在加速器里测到的速度会比实际偏低。这也是默认"恋旧"的原因。
- 只接管 DASH 分段（`.m4s`）中较大的 Range 请求（≥128KB）；初始化段、索引这类小请求直接放行。
- 不能突破清晰度和会员限制：只是换节点、并行下载，拿的仍是 B 站给你的那份文件。
- 内容一致性只能在多个节点之间互相比对。如果一段数据从头到尾都由同一个节点提供，脚本无法判断它对不对，这一点和原播放器一样。
